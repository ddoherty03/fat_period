* Introduction
~FatPeriod~ provides a Ruby ~Period~ class for dealing with time periods of
days, that is ranges whose endpoints are of class ~Date~.  It's target is
financial applications, but it serves well for any application where periods
of time are useful.  It builds on the [[https://github.com/ddoherty03/fat_date][fat_date]] gem, which provides
enhancements to the ~Date~ class, especially its class method ~Date.spec~ for
interpreting a rich set of "specs" as the beginning or end of a variety of
calendar-related periods.

In addition, set operations are provided for Period, as well as methods for
breaking a larger periods into an array of smaller periods of various 'chunk'
sizes that correspond to calendar-related periods such as days, weeks, months,
and so forth.

* Usage
** Constant ~Period::FOREVER~

The ~Period~ class depends on the extensions to ~Date~ made by the ~fat_core~
gem, which you can read about [[https://github.com/ddoherty03/fat_core][here]].  It defines a constant, ~Period::FOREVER~,
which is defined as extending from ~Date::BOT~ to ~Date::EOT~, which are
defined in ~fat_date~ as 1900-01-01 and 3000-12-31, respectively and define
the beginning of time and end of time for practical commercial purposes.  The
constant is not frozen, so you can re-define it to your liking.

** Construction of Periods
*** ~Period.new~
A Period is constructed with two arguments for the begin and end date.  The
begin date must be on or before the end date.  Each argument can be (1) a
Date, (2) a string parseable as a Date by the Date.parse method, or (3) an
object that responds to ~#to_s~ and can be parsed as a Date by Date.parse:

#+begin_SRC ruby
  p1 = Period.new(Date.today, Date.today + 30)
  p2 = Period.new('Nov 22, 1963', Date.today)
  p3 = Period.new('1961-01-21', '1963-11-22')
  [[p1.to_s], [p2.to_s], [p3.to_s]]
#+end_SRC

#+RESULTS:
#+begin_example
| 2026-11-05 to 2026-12-05 |
| 1963-11-22 to 2026-11-05 |
| 1961-01-21 to 1963-11-22 |
#+end_example

#+begin_src ruby
  ["Camelot lasted #{p3.length} days"]
#+end_src

#+RESULTS:
#+begin_example
| Camelot lasted 1036 days |
#+end_example

*** ~Period.parse~
A more convenient way to construct a period is provided by ~Period.parse~.  It
takes two strings as its arguments, a mandatory "from-spec" and an optional
"to-spec":

A "spec" is a string designating some period of time.  There are many ways of
specifying a period, which are detailed below.

**** With Only a From-Spec

If only a from-spec is given, it defines both the beginning and end of the
overall period:

#+begin_src ruby
  tab = []
  tab << ['From Spec', 'Result']
  tab << nil
  froms = ['2020', '2020-2Q', '2020-W15', '2020-09', '2020-09-A', '2020-09-iii']
  froms.each do |f|
    tab << [f, Period.parse(f).inspect]
  end
  tab
#+end_src

**** With Both a From-Spec and To-Spec
But, if a to-spec is also given, the from-spec defines the beginning of the
period and the to-spec defines the end of the period. In particular, the
beginning of the period is the first day of the from-spec and the end of the
period is the last day of the to-spec:

#+begin_src ruby
  tab = []
  tab << ['From Spec', 'To Spec', 'Result']
  tab << nil
  from_tos = [['2020', '2020-2Q'], ['2020-2Q', '2020-W15'], ['2020-W15', '2020-09'], ['2020-09', '2020-09-A'], ['2020-09-A', '2020-09-iii']]
  from_tos.each do |f, t|
    tab << [f, t, Period.parse(f, t).inspect]
  end
  tab
#+end_src

**** Using Skip Modifiers
One new feature of FatDate is the ability to add a "skip modifier" to the end
of a date spec to skip forward or backward to the first day-of-week either on
or before/after the date given by the spec.  For example, the following
demonstrates that one can set the 'to' spec to the /last/ Wednesday of 2025 or
the last Wednesday /before/ the end of 2025.  Using '>' or '>=' specified
skipping forward instead.

#+begin_src ruby
  tab = []
  tab << ['From Spec', 'To Spec', 'Result', 'Description']
  tab << nil
  from_to_descs = [['2025-2Q', '2025<=Wed', 'From 2q to last Wednesday of 2025'],
                   ['2025-2Q', '2025<Wed', 'From 2q to last Wednesday /before/ the end of 2025'],
                   ['2012-11', '2012-11<=Thur', 'November 2012 through last Thursday'],
                   ['2012-11', '2012-11-4Thur', 'And through Thanksgiving (not always the /last/ Thursday!)']
                  ]
  from_to_descs.each do |f, t, d|
    tab << [f, t, Period.parse(f, t).inspect, d]
  end
  tab
#+end_src

*** ~Period.parse_phrase~
For example:

The ~Period.parse_phrase~ method will take a string having a 'from', 'to', and
'per' clause and return an Array of Periods encompassing the same period as
~Period.parse~, but optionally broken into sub-periods each having the length
specified by the 'per' clause.  ~Period.parse_phrase~ always returns an Array
of Periods even if there is no 'per' clause and the Array has only one
member. If there is no 'to' clause, the returned period is from the start of
the 'from' period to its end.  If there is neither a 'from' or a 'to' clause,
it tries to interpret the beginning of the phrase as a valid spec and uses it
as a 'from' clause.

#+begin_src ruby
  tab = []
  tab << ['k', 'Sub Period']
  tab << nil
  pds = Period.parse_phrase('from 2025 to 2025-3Q per month')
  pds.each_with_index do |pd, k|
    tab << [k, pd.inspect]
  end
  tab
#+end_src

*** ~Period.ensure~
~Period.ensure~ tries to interpret its argument as a ~Period~ and returns it;
otherwise it throws an ~ArgumentError~ exception:

- if the argument responds to the ~to_period~ method, it invokes that on the
  argument and returns it;
- if the argument is a ~String~, it uses ~Period.parse_phrase~ to try to
  interepret it as a ~Period~;
- if it is already a ~Period~, it just returns the argument;
- otherwise, it throws an ~ArgumentError~ exception.


 #+begin_src ruby
   class ContainingMonth
     def initialize(dat)
       @dat = Date.ensure(dat)
     end

     def to_period
       Period.month_containing(@dat)
     end
   end

   cm = ContainingMonth.new('2025-09-22')
   Period.ensure(cm)
  #+end_src

  #+RESULTS:
  #+begin_example
  Period(2025-09-01..2025-09-30)
  #+end_example

#+begin_example
Period(2025-09-01..2025-09-30)
  #+end_example

*** ~#to_s~
~Period#to_s~ does ~String~ conversion but using compact notation for
years, halves, quarters, and months if possible; otherwise, it gives
~first~ and ~last~ explicitly:

#+begin_src ruby
  specs = [
    'from this_year',
    'from 2026-2H',
    'from 2026-3Q',
    'from 2026-10',
    'from 2026-10 to 2026-10-30'
  ]
  tab = []
  tab << ['Spec', '#to_s']
  tab << nil
  specs.each do |s|
    pd = Period.parse_phrase(s).first
    tab << [s, pd.to_s]
  end
  tab
#+end_src

#+RESULTS:
#+begin_example

| from 2026-2H               | 2026-2H                  |

| from 2026-10 to 2026-10-30 | 2026-10-01 to 2026-10-30 |

** Comparison
The ~Period~ class includes ~Comparable~ so periods can be compared
directly.  Period are compared by ~first~, and if those are the same,
then by ~last~, and those using normal ~Date~ comparison.

#+begin_src ruby
  spec_pairs = [
    ['from 2026', 'from 2026-1H'],
    ['from 2026', 'from 2026-2H'],
    ['from 2016-05', 'from 2016-05 to 2016-06'],
    ['from 2026', 'from 2026-2H'],
    ['from 2026', 'from 2025'],
    ['from 2010-09', 'from 2010-09'],
  ]
  tab = []
  tab << ['Period1', 'Period2', 'Period1 <=> Period2']
  tab << nil
  spec_pairs.each do |s1, s2|
    p1 = Period.parse_phrase(s1).first
    p2 = Period.parse_phrase(s2).first
    tab << [p1.to_s, p2.to_s, p1 <=> p2]
  end
  tab
#+end_src

#+RESULTS:

|    2026 | 2026-2H                  | -1                  |

*** ~#chunks(size: :month, partial_first: true, partial_last: true, round_up_last: false)
You may want to divide a year into months, or a quarter into
semi-months.  For this ~FatTable~ provides ~Period#chunks~.  By default,
the first and last chunks will be partial, the first starting at
~Period#first~ regardless of whether it is a full chunk and the last
ending at ~Period#last~ regardless of whether it is a full chunk.  But
this can be altered at the cost of not fully spanning the subject
~Period~.

- ~partial_first~ :: if set ~false~, the first chunk will be a
  full-sized chunk at the possible cost of starting later than
  ~Period#first~; it is ~true~ by default.
- ~partial_last~ :: if set ~false~, the last chunk will be a
  full-sized chunk at the possible cost of ending earlier than
  ~Period#last~; it is ~true~ by default.
- ~round_up_last~ :: if set ~true~, the last chunk returned may extend
  beyond ~Period#last~ if it needs to in order to make it whole; it is
  ~false~ by default.

partial first and last week by default:

Similar to ~Period.overlaps_among~ except that it returns true only if

Returns whether the given ~Array~ of ~Periods~ "span" the subject

Returns an ~Array~ of ~Period~s representing the gaps within the subject

the subject ~Period~.  Ordering among the given ~periods~ does not
matter.


** Interest Day-count fraction (~#year_fraction~)
For interest-related calculations, the methods by which accrued interest
is allocated to a partial ~Period~ are numerous and subtle.  Rather than
solve this problem over-and-over, ~FatPeriod~ aims to implement a single
method that solves this problem once-and-for-all.

The dates that correspond to the notation in Wikipedia's [[https://en.wikipedia.org/wiki/Day_count_convention][Day count
convention]] article, which was used as a reference for ~FatPeriod~'s
implementation, are as follows:

- ~first~ is Date1, the start of accrual.
- ~date2~ is Date2, the payment or settlement date, supplied as a ~Date~ or a
  date string.  It must fall within the Period, including its endpoints.
- ~last~ is Date3, the next coupon payment date.  For ICMA, construct the
  Period with consecutive coupon boundaries.

~Period#year_fraction~ returns a ~BigDecimal~ factor for calculating
interest from ~first~ to a given payment or settlement date.  Usually
this is a fraction of a year: multiply the principal by the annual rate
and this factor to calculate accrued interest.  The default convention
is *30/360 US* (~convention: 1~).

#+begin_example
period.year_fraction(date2, convention: 1, eom: true, maturity_date: nil)
#+end_example

Day counts use elapsed days, without adding one as ~Period#size~ does.  For
example, January 1 to July 1 is the reference period for a coupon paid on
July 1; use July 1 as ~last~, rather than June 30.  Passing ~last~ as the
settlement date calculates the full coupon's factor.

#+begin_src ruby
period = Period.new('2024-01-01', '2024-07-01')
pay_date = '2024-04-01'
principal = BigDecimal('1000')
rate = BigDecimal('0.05')

tab =
  [['Principal', principal.to_s('F')],
   ['Rate', rate.to_s('F')],
   ['Period', period.to_s],
   ['Payment Date', pay_date]]
tab
#+end_src

#+RESULTS:
#+begin_example
| Principal    |                   1000.0 |
| Rate         |                     0.05 |
| Period       | 2024-01-01 to 2024-07-01 |
| Payment Date |               2024-04-01 |
#+end_example

#+begin_src ruby :results value table
tab2 = []
tab2 << ['Convention', 'Factor', 'Interest']
tab2 << nil
0.upto(11) do |conv|
  factor = period.year_fraction(pay_date, convention: conv)
  interest = principal * rate * factor
  tab2 << [conv, factor.round(4).to_s('F'), interest.round(2).to_s('F')]
end
tab2
#+end_src

*** Choosing a convention
The convention numbers are specific to ~FatPeriod~; they are not Excel's
~YEARFRAC~ basis numbers.  Supply ~convention: 0~ explicitly for Bond Basis.
The ISDA references below are to Section 4.16 of the /2006 ISDA Definitions/.

| Convention | Name                | Reference                       |
|------------+---------------------+---------------------------------|
| 0          | 30/360 Bond Basis   | ISDA 4.16(f)                    |
| 1          | 30/360 US (default) | 4.16(f), plus US February rules |
| 2          | 30E/360             | ISDA 4.16(g)                    |
| 3          | 30E/360 ISDA        | ISDA 4.16(h)                    |
| 4          | Actual/Actual ICMA  | ISDA 4.16(c); ICMA Rule 251     |
| 5          | Actual/Actual ISDA  | ISDA 4.16(b)                    |
| 6          | Actual/365 Fixed    | ISDA 4.16(d)                    |
| 7          | Actual/360          | ISDA 4.16(e)                    |
| 8          | Actual/364          | Wikipedia's Actual/364 section  |
| 9          | Actual/365L         | Wikipedia's Actual/365L section |
| 10         | Actual/Actual AFB   | Wikipedia's AFB discussion      |
| 11         | 1/1                 | ISDA 4.16(a)                    |

For convention 1, ~eom: true~ (the default) applies the February
end-of-month rules for investments that pay at month end.  Set ~eom:
false~ to omit those February adjustments.  The remaining 30/360
adjustments still apply.

For convention 3, ~maturity_date:~ accepts a ~Date~ or date string and
identifies the investment's final maturity.  It is irrelevant for the
other conventions and is ~nil~ by default.  Under convention 3, when
settlement (i.e., ~date2~) is that date and is the last day of February,
its day number is left unchanged.  Otherwise the usual month-end
adjustment applies.

#+begin_src ruby
  final_coupon = Period.new('2023-08-31', '2024-02-29')
  ordinary = final_coupon.year_fraction('2024-02-29', convention: 3)
  at_maturity = final_coupon.year_fraction(
    '2024-02-29', convention: 3, maturity_date: '2024-02-29'
  )
  [ordinary.to_s('F'), at_maturity.round(10).to_s('F')]
#+end_src

#+RESULTS:
#+begin_example
| 0.5 | 0.4972222222 |
#+end_example

*** Actual-day conventions and boundaries
ICMA (4) divides elapsed days by the product of payment frequency and elapsed
days in the full coupon period.  Frequency is inferred from the full period's
length.  For example, both a full 181-day half-year coupon and a full 184-day
half-year coupon have a factor of 0.5, but their daily accruals differ.

#+begin_src ruby
  coupon = Period.new('2024-01-01', '2024-07-01')
  partial = coupon.year_fraction('2024-04-01', convention: 4)
  full = coupon.year_fraction(coupon.last, convention: 4)
  [partial.to_s('F'), full.to_s('F')]
#+end_src

#+RESULTS:
#+begin_example
| 0.25 | 0.5 |
#+end_example

ICMA supports regular coupon periods only; it does not construct notional
coupon schedules for irregular first or final coupons.  Frequency inference
allows the same 10% length tolerance as ~chunk_name~ for monthly and longer
periods.  An unrecognizable length raises ~ArgumentError~ for conventions
that require frequency (4 and 9).

ISDA Actual/Actual (5) splits the elapsed interval at calendar-year boundaries,
using 365 or 366 for each portion.  Conventions 6, 7, and 8 use fixed
denominators of 365, 360, and 364 respectively.

Actual/365L (9) follows the Wikipedia article's settlement-date rule: for
annual payments, it uses 366 if February 29 falls after ~first~ and on or
before settlement, otherwise 365.  For other frequencies, it uses the number
of days in the settlement year.  The full period determines frequency, not
the leap-day test interval.

AFB (10) counts complete years backwards from settlement, then calculates the
remaining initial fraction.  It uses the ISDA backward-counting February
adjustment described in the article: a February 28 anniversary moves to
February 29 when the preceding year is a leap year.  The remaining fraction
uses 366 only when it includes February 29, counting its start but excluding
its end.

Equal start and settlement dates return zero for conventions 0 through 10.
Convention 11 (1/1) always returns one, even for equal dates: it applies the
full contractual rate without prorating for time.  Invalid convention numbers
or settlement dates outside the Period raise ~ArgumentError~.

- [[https://en.wikipedia.org/wiki/Day_count_convention][Wikipedia: Day count convention]] gives the formulas, naming variants, and
  discussion of the conventions implemented here.
- [[https://www.isda.org/book/2006-isda-definitions/][2006 ISDA Definitions]], Section 4.16, /Day Count Fraction/, is the primary
  source for most of these rules.  A [[https://www.sc.com/en/uploads/sites/66/content/docs/2006-ISDA-Definitions.pdf][PDF copy hosted by Standard Chartered]]
  contains the section on printed pages 11-13.  Section 4.16(f) defines Bond
